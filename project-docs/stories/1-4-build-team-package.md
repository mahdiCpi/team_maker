# Story 1.4: Build a self-contained Team Package

Status: done

## Story

As a user,
I want a valid spec turned into a runnable package,
so that the team exists independently of the builder.

## Acceptance Criteria

1. **Given** a schema-valid `TeamCreationRequest` (Team Spec), **When** `PipelineRunner.run(request)` builds it, **Then** a self-contained Team Package is written to `request.output_path` containing, at minimum: `README.md`, `team_config.yaml`, `routing_config.yaml`, `run_example.py`, `requirements.txt`, `generation_report.md`, one `agents/<role>.yaml` per agent, one `tasks/<name>.yaml` per task, and `docs/how_to_run.md` + `docs/how_to_extend.md` + `docs/model_routing.md` — this is the manifest `PipelineRunner._build_manifest` already assembles and `ArtifactWriter.write()` already writes to disk. (FR-5, AD-1)
2. **Given** that same build, **When** it completes, **Then** `OutputValidator.validate(output_path, team)` runs against the just-written files and the returned `PipelineResult.validation` is a `ValidationResult(passed, issues[], warnings[])`; for a clean package, `passed is True` and `issues == []`. (FR-7)
3. **Given** a package missing a required file, missing an agent's `agents/<role>.yaml`, or missing a task's `tasks/<name>.yaml`, **When** validated, **Then** `ValidationResult.issues` contains the specific human-readable string for that failure (`"Missing required file: <path>"` / `"Missing agent config: agents/<role>.yaml"` / `"Missing task config: tasks/<name>.yaml"`) and `passed is False`. (FR-7)
4. **Given** a package containing a malformed YAML file, **When** validated, **Then** `ValidationResult.issues` contains `"Malformed YAML in <path>: <parse error>"` and `passed is False`. (FR-7)
5. **Given** the `team-maker create` CLI command (the direct CLI surface for "spec → package"), **When** the build's validation fails, **Then** the CLI prints the exact `issues`/`warnings` bullet list via the existing `_print_result` and exits with code 2; **when** validation passes, **Then** it prints a "PASSED" panel with no issues/warnings block and exits 0 — the same pass/fail-reporting contract `compose --build` already relies on. (FR-7; consistency)
6. **Given** this story's scope, **When** implementing it, **Then** no behavioral changes are made to `generators/`, `validation/validator.py`, `artifacts/writer.py`, or `pipeline/runner.py` — AD-1 ("Factory stays a pure factory") — this story closes a CLI-level test-coverage gap and confirms the existing factory already satisfies AC 1–5; it does not re-implement generation or validation. (AD-1)

## Dev Notes

### What this story is (and is not)
- **Is:** confirmation-and-test-coverage work against an **already-implemented** Factory build+validate pipeline (`PipelineRunner` → `ArtifactWriter` → `OutputValidator`), plus one genuinely missing piece: CLI-level tests for the `create` command (today's only tests that exercise a build end-to-end through the CLI go through `compose`/`compose --build`, not `create`). FR-5 and FR-7 are labeled "Factory (existing, reused)" in `project-docs/epics.md`'s FR Coverage Map for exactly this reason.
- **Is NOT:** a rewrite or extension of `generators/`, `validation/validator.py`, `artifacts/writer.py`, or `pipeline/runner.py`. AD-1 ("Factory stays a pure factory") is `[ADOPTED]` and explicit: "New behavior goes in Composer/Runtime/adapters, never inside the factory." If, while implementing, the factory is found to genuinely violate an AC clause, stop and flag it rather than silently patching factory internals — that would be a scope decision for the user, not an implicit refactor.
- **Is NOT** Story 1.5 (Run a team and return results) — this story ends at "package written and validated," never executes agents. Story 1.3's own Dev Notes already drew this line: "'run now' only builds via `PipelineRunner`; it never executes agents" (`1-3-conversational-tuning-run-now.md:67`).
- **Is NOT** about the per-role provider-key bridging gap noted in `deferred-work.md:44` ("`compose --build` doesn't bridge per-role provider keys") — that's explicitly Story 1.6/FR-10 (Runtime credential gating), not a Factory build/validate concern; the factory itself degrades gracefully today ("API unreachable — trust the YAML").

### Architecture constraints (binding)
- **AD-1 — Factory stays a pure factory.** Generators remain pure string producers (no disk/network/clock access); only `ArtifactWriter` touches disk; provider routing stays data-driven (never branch on provider name); output is idempotent (already tested: `test_pipeline_is_idempotent`). [Source: ARCHITECTURE-SPINE.md#AD-1]
- **AD-8 — single LLM/Provider port.** Not directly exercised by this story (no new LLM calls), but the factory's routing output (`routing_config.yaml`) must keep reflecting whatever the Composer/CLI resolved — don't reintroduce provider-name branching anywhere touched. [Source: ARCHITECTURE-SPINE.md#AD-8]

### Project conventions (must follow — from project-context.md)
- `from __future__ import annotations`; full type hints; snake_case; ruff line-length 100. Run `make lint`/`make fmt`.
- Generators are unit-tested in-memory (no filesystem); filesystem behavior belongs in integration tests using `tmp_path`. The new CLI test file is filesystem-touching (via `CliRunner` + `tmp_path`) — put it in `tests/unit/` anyway, matching where `test_cli_compose.py` already lives (this repo's existing convention groups "CLI-level" tests under `tests/unit/`, not `tests/integration/`, regardless of disk I/O).
- `generation_report.md` is intentionally excluded from `OutputValidator._REQUIRED_FILES` because it's written *after* validation — don't "fix" this by adding it to the required-files check.
- CLI exit codes are a preserved contract: `0` ok, `1` config/load/conflict error, `2` validation failed. (`project-context.md` "Critical Don't-Miss Rules")
