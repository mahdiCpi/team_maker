## Architectural & implementation lessons

- A schema can silently outgrow its own documentation during active feature development — `data-models.md` was written for an 11-field pre-merge schema; the real `request.py` had grown to 21 fields with five undocumented `_pre_process` normalizations by the time Story 0.5 looked. The fix required re-deriving the doc from source line-by-line, not patching a paragraph.
- The mitigation that worked: the adversarial review's Edge Case Hunter layer re-verified every doc claim against the live source rather than trusting the diff's own prose — this is exactly what caught that `ProviderConfig.base_url` is documented as functional but silently dropped by both routing-resolution paths, and that the `planning_llm`/`default_llm` fallback-chain note only holds for one of two generation strategies.

## Testing & code-review gaps discovered

- The review process matured mid-epic: Stories 0.1/0.2 got a lighter single-pass adversarial review ("APPROVE, zero findings"); Stories 0.3/0.4/0.5 used the full three-layer `bmad-code-review` (Blind Hunter + Edge Case Hunter + Acceptance Auditor). The fuller process is the one that caught substantive issues — including, in Story 0.4, a real AC violation where a per-agent `api_key_env` override could be silently shadowed by an auto-filled `KeyConfig` entry (a genuine credential-resolution bug, not a style nitpick).
- Recommendation: make the three-layer review the Epic 1+ default, not an epic-0-only upgrade.

## Git, branching, and process lessons (CLAUDE.md)

- CLAUDE.md's rules 5 ("commit and push each branch after review") and 6 ("every branch must exist on remote") are literally the **last two commits on `epic_0`** — written after Stories 0.1 through most of 0.4 were already done.
- Verified against the raw git graph: `story_0_1`, `story_0_2`, `story_0_3`, and `story_0_4` all point at commits that are already inside `epic_0`'s own linear history — no merge commits exist. That work happened as direct commits on `epic_0` itself; the story-named branches are pointer labels attached afterward for remote-visibility compliance, not real isolated branches merged back per rules 1–4.
- **Story 0.5 is the first story in this epic to fully follow CLAUDE.md rules 1, 2, 5, and 6**: branched from `epic_0` before work started, pushed to remote immediately, developed and code-reviewed on its own branch, and merged back only after acceptance (`story_0_5` → `epic_0`, fast-forward, `540053a`, done during this retrospective).
- Story 1.1 ("load keys and report available models") has no branch at all, ever — its code arrived via the `main`-branch merge of `guru-explore`, before Epic 0 or these CLAUDE.md rules existed. Historically explainable, not a rule violation, but worth a conscious decision rather than silently carrying it forward.

**Recommendations for future epics:**
1. Make the three-layer `bmad-code-review` the default from the first story of an epic, not something adopted partway through.
2. Verify every new epic/story branches from an up-to-date base before work starts — apply this explicitly when Epic 1's branches are recreated.
3. Sweep long-lived pre-existing lint debt (the `test_planner_mapper.py` findings) in a dedicated pass rather than letting it silently roll forward.
4. Clean up automation-run branches (`archon/task-*`) once confirmed unneeded, to keep the remote network graph legible.
