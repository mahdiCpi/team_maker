# Story 1.5: Run a team and return results

Status: done

## Story

As a user,
I want to run a built team against a goal and get results,
so that the agents do the work instead of me relaying between chatbots.

## Acceptance Criteria

1. **Given** a Team Package already built and validated by the Factory (Story 1.4) on disk, and a goal string, **When** the Runtime runs it, **Then** it loads the package's `team_config.yaml`/`agents/*.yaml`/`tasks/*.yaml`/`routing_config.yaml` back into an in-memory team (independent of any in-process object from the build step — a package built earlier, or by someone else, must be runnable from disk alone). (FR-8, AD-1 — Runtime never re-generates the package, only reads it)
2. **Given** that loaded team, **When** it executes, **Then** tasks run via CrewAI (the v1 Runtime engine, AD-6) in an order consistent with each task's `dependencies` — never before a task it depends on. (FR-8, FR-9)
3. **Given** a task with one or more `dependencies`, **When** its agent runs, **Then** that agent's prompt/context includes the upstream (dependency) tasks' outputs — "downstream agents receive upstream outputs" is satisfied via CrewAI's own `Task.context` mechanism, not a bespoke string-passing scheme. (FR-9)
4. **Given** each agent's `routing_config.yaml` entry (`provider`, `model`, optional `api_key_env`), **When** the Runtime builds that agent's LLM client, **Then** credentials are resolved from the Key Config (AD-9) and passed as an explicit, per-agent credential — never a global/shared `os.environ` mutation (AD-7's "no global env fallback" principle, applied here even though the multi-provider *conformance test* proving it is Story 1.6's job). (AD-7, AD-9)
5. **Given** a run completes, **When** results are returned, **Then** the caller receives both the final output and every task's individual output, in batch, as a structured result (not only console text) — this is the "results interface" AD-13 requires and nothing in the codebase currently models. (FR-11, AD-13)
6. **Given** the `team-maker run` CLI command, **When** it is invoked with `--package <dir>` and a goal, **Then** it prints the final result and a per-task breakdown and exits `0` on success; a missing/malformed package, a non-CrewAI `primary_framework` package, or any execution failure prints a plain-language message and exits `1`. (FR-8, FR-11; CLI consistency with `create`'s exit-code discipline)
7. **Given** this story's scope, **When** implementing it, **Then** the Runtime never decides team membership/roles and never mutates the on-disk package (AD-5 — Composer authors, Factory builds, Runtime only executes); credential *fail-fast-naming-the-missing-provider* behavior (FR-10) and the multi-provider *conformance test* (AD-7) remain explicitly out of scope — deferred to Story 1.6, matching the precedent already set by Stories 1.2/1.4. (AD-5; scope boundary)

### Addendum: why the CrewAI import is deferred inside the function, not at module top
`executor.py` imports `CrewAIExecutionEngine` lazily inside `run_team_package`, not at module scope. This matters beyond style: `team_maker/cli.py` imports from `runtime/executor.py` for the new `run` command (Task 7). If that import chain pulled in CrewAI at module load time, then merely running `team-maker create`/`compose`/`keys status` — commands that have nothing to do with execution — would fail for any install that skipped the optional `runtime` extra. Deferring the import means CrewAI is only required at the moment `run_team_package()` actually executes without an explicit engine, preserving `crewai` as a genuinely optional dependency exactly as the new `pyproject.toml` group implies.

## Dev Notes

### What this story is (and is not)
- **Is:** the first genuinely new (not reuse-only) infrastructure since Epic 0/1 began — a real in-process Runtime that loads a built Team Package from disk and executes it via CrewAI, producing a structured batch result. Unlike Story 1.4 (pure confirm-and-test-the-existing-factory), there is **no prior art to reuse** for execution — confirmed by exhaustive search: no `team_maker/runtime/` directory, no `run` CLI command, no `RunResult`-shaped type, no topological-sort logic, and the generated `run_example.py` template itself doesn't even respect task `dependencies` order today.
- **Is NOT** a rewrite of the generated `run_example.py`/`crewai_runner.py.j2` template — that remains the *standalone* runner a user can invoke directly with `python run_example.py` after `pip install`ing the generated package's own requirements. This story adds a **second, separate** way to run a team: in-process, from team_maker's own CLI, against an already-built package. The two can diverge in behavior for now (e.g. the template still doesn't do dependency-order or `context=` wiring) — reconciling them is not this story's job.
- **Is NOT** Story 1.6 (multi-provider conformance test, fail-fast-on-missing-key with the provider named) — this story builds the *mechanism* (explicit per-agent credentials, never global env), Story 1.6 builds the *proof* and the *fail-fast UX*. This mirrors how Story 1.2 built spec composition and a later story added its conformance/hardening pass.
- **Is NOT** a change to the Factory (`PipelineRunner`/`OutputValidator`/`ArtifactWriter`/generators) or to the existing codegen `RuntimeEngine` port/`adapters/runtime_engines/` — those stay completely untouched (AD-1).

### Architecture decision this story makes — flagged for confirmation
The architecture spine's structural seed (`ARCHITECTURE-SPINE.md:179-197`) explicitly lists `team_maker/team_maker/runtime/` and `team_maker/team_maker/adapters/runtime_crewai/` as **NEW** additions, and AD-6 states "v1 executes teams via a CrewAI adapter behind `RuntimeEngine`; core/runtime depends only on the port" — read literally, this means CrewAI execution happens **inside team_maker's own process**, which is what this story builds.

This directly supersedes two now-stale documents, the same way Story 1.4 found `data-models.md` §4 stale:
- `project-context.md` ("Architecture invariants"): *"team_maker is a factory, not a runtime... Do NOT add agent-execution logic to the `team_maker/` package (that belongs in a future `runner/`...)"* — written 2026-07-04, **before** the architecture spine (finalized 2026-07-06) put `composer/` and `runtime/` inside `team_maker/team_maker/` as new subpackages. Precedent already established this supersession: Story 1.2/1.3 already put `composer/` (agent-composition logic) inside `team_maker/`, and no review ever flagged that as violating this rule.
- `project-docs/vision-and-target-architecture.md` (2026-07-04, explicitly labeled "forward-looking design analysis... nothing in this document is built yet"): recommends Claude Code as an *external* L2 orchestrator driving team_maker via subprocess/MCP, with the runtime as a separate top-level `runner/`.
