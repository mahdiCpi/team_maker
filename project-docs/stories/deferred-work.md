## Deferred from: code review of story-1.2 (2026-07-26)

- **`compose --build` doesn't bridge per-role provider keys** — only the authoring provider's key is bridged into `os.environ` before `composer.compose()` runs; if the composed spec routes roles to `openai`/`google`/`xai` (per the Composer's own word→provider alias table), nothing bridges those keys before `PipelineRunner().run()` executes. - **Generic exception printing in `compose` could echo SDK-embedded secrets** — `except Exception as exc: ... escape(str(exc))` around `composer.compose(intent)` prints the raw exception string, which could in theory contain credential fragments from an underlying SDK error. AC3 explicitly scopes the retry budget to schema-validation failures, not general resilience; revisit if flaky LLM calls become a real-world problem.
- **No repair-attempt progress feedback in `compose`'s non-quiet output** — a UX nicety (e.g. "repair attempt 2/3"), not required by any AC.
- **`compose --model` cannot override the authoring provider, only the model string** — matches Task 4's literal spec (only `--model` was requested); revisit if a `--provider` override becomes a real user need.

## Deferred from: code review of story-1.3 (2026-07-27)

- **Only `ComposerError` is caught around `session.refine()` in the interactive loop** — any other exception (network/transient/parse failure) is uncaught there and crashes the whole conversation (exit 1) instead of letting the user retry that turn. Consistent with Story 1.2's own established precedent that retries are scoped to schema-validation failures only, not general resilience.
- **No cap on conversation turns or consecutive failed-refinement attempts** in `compose --interactive` — a confused user or scripted stdin can drive unbounded LLM spend with zero guardrail.
- **No `KeyboardInterrupt` handling in the interactive loop** — Ctrl+C while blocked on `input()` produces a raw traceback; no existing convention for this elsewhere in the CLI either.
- **`ComposerSession` has no undo/rollback** beyond asking the LLM to revert a change in a further turn. AD-11 only requires in-memory current state for v1; no history/versioning requirement in Story 1.3's ACs.
- **Prompt/token cost grows with spec size on every refinement turn** — the full current spec is re-embedded on each `refine()` call with no truncation, diffing, or summarization strategy. A real scalability concern for larger specs or longer conversations, not required by this story.
- **"Apply only this change" is prompt-only guidance, never code-verified** — nothing diffs the LLM's output against the prior spec to catch silent drift in fields the user didn't ask to change. Matches Story 1.2's precedent that prompt-level LLM guidance is acceptable and only schema-level issues are code-enforced via the repair loop.

## Deferred from: story-1.6 implementation (2026-08-02)

- ~~**The provider catalog admits providers the v1 runtime engine cannot actually construct.**~~ — **resolved by the Story 1.6 code review (2026-08-02).** CrewAI 1.14.6's native provider list is `openai, anthropic, claude, azure, azure_openai, google, gemini, bedrock, aws, openrouter, deepseek, ollama, ollama_chat, hosted_vllm, cerebras, dashscope` — it has **no** native `groq` or `xai`, and this repo does not install the `litellm` fallback. So an agent routed to `xai` **with a valid XAI_API_KEY present** used to pass the pre-run gate and then fail at `LLM(...)` construction with an `ImportError` reported as a generic "Run failed".

  The original entry got two things wrong, both corrected by the review:
  1. **`google` was omitted, and it was the worst case.** crewai needs the `crewai[google-genai]` extra to call Google natively (`google-generativeai` in the `all` extra is a *different* package), so a `GOOGLE_AI_API_KEY` produced a crash while having *only* an `OPENROUTER_API_KEY` worked — adding the correct key broke the run.
  2. **"`groq` is luckier: it is `openrouter_reachable`, so it works whenever an OpenRouter key is present" was false.** An OpenRouter model id is `<model-creator>/<model>` — the organisation that made the weights, not the company serving them. Groq is an inference *host* and has no vendor namespace, so `openrouter/groq/<model>` is not a valid id; the run was admitted and then rejected by the gateway.

  Fix: a `runtime_supported` flag (plus `unsupported_reason`) on `Provider`, checked by `classify()` via the new `STATUS_UNSUPPORTED_BY_RUNTIME`. `groq`/`xai`/`google` are now refused by the gate before any LLM is constructed, with a message that does *not* ask for a key that would not help; `google`, being a genuine OpenRouter vendor, is pointed at the gateway instead. `groq` had `openrouter_reachable` removed. Re-opening any of these is a one-line catalog change once the engine can reach them.

## Deferred from: story-1.7 implementation (2026-08-02)

- **Partial transcripts on a failed run are not returned.** Story 1.7's AC is scoped to "**When** it completes" — if `kickoff` raises, the recorder's context manager unregisters cleanly but the entries collected so far are discarded along with the exception. PRD Open Q5 ("what happens when a Provider errors mid-run; are partial results returned?") is still open (`prd.md:457-460`), and `EXPERIENCE.md:91` explicitly defers partial-results behavior to it. A partial transcript is arguably *more* valuable than a complete one — it is what tells the user where the run died. Closing this means deciding whether `MissingCredentialsError`-style structured failure should carry a transcript, which is a product decision, not a routing one.
- **Concurrent runs in one process corrupt each other's transcripts.** The crewai event bus is a process-global singleton and its handlers run on a shared worker pool, so two simultaneous `run_team_package` calls each record the other's events. **Measured during the Story 1.7 code review** (two threads held inside `kickoff` by a barrier): run A came back with every entry duplicated, run B *lost* an entry and gained a `task='unknown'`, and the two runs' `emission_sequence` values collided outright — the counter is ContextVar-scoped and restarts at 1 per run, so sorting cannot separate them. `__exit__`'s `flush()` also waits on all process-wide pending futures, so each run blocks on the other's handlers. v1 is single-run-at-a-time (the CLI cannot do otherwise), but Story 4.2's HTTP endpoint is exactly where this breaks. Fix candidates: filter captured events by the run's own task/agent id set, or serialize runs behind a lock in the API layer.
- **The generated `crewai_runner.py.j2` template captures no transcript.** FR-27 is satisfied for the in-process Runtime only; a user running the standalone `run_example.py` from a Team Package still sees only the final answer. Out of scope here for the same reason as Stories 1.5 and 1.6 — it is a codegen change (AD-1), and that template also still carries the known hierarchical-Crew bug (`deferred-work.md:70`) and the AD-7 global-env gap. Whoever fixes one should fix all three together.
- **The transcript conformance test inherits the `importorskip` hole.** `tests/conformance/test_transcript_conformance.py` skips silently where crewai is absent, exactly as the AD-7 gate does (already logged above). This is now a second instance of the same gap rather than a new one; closing it wants a required-marker or a dedicated CI lane that fails when conformance does not actually execute.

## Deferred from: code review of story-1.7 (2026-08-02)

- **ANSI/OSC escape sequences in transcript content reach the terminal verbatim.** `rich.markup.escape` neutralizes `[` only; it does nothing to `ESC`. An agent echoing colourised tool output — or a prompt-injection payload — can move the cursor, clear the screen, or emit an OSC-8 hyperlink when a user runs `team-maker run --transcript`. Confirmed by CLI probe. The written file is unaffected. Not fixed here because stripping control characters is a display-sanitization convention the codebase does not yet have (`deferred-work.md:45` already notes the absence of a scrubbing convention), and getting it wrong would mangle legitimate content.
- **Six deep crewai internal import paths are now load-bearing for running a team at all.** `crewai_execution_engine.py` imports `transcript_capture` at module scope, which imports from `crewai.events.types.*` and `crewai.utilities.string_utils` — non-public paths (`AgentLogsExecutionEvent` is a *logging* event; `sanitize_tool_name` is a utility helper). If any move in a crewai upgrade, the engine module fails to import and `run` cannot execute — an observability regression becomes total loss of the feature. Candidate fix: import the event classes lazily inside `_subscribe` behind a `try/except ImportError` that degrades to an empty transcript, so the run still works.
- **A renamed or removed `emission_sequence` would silently discard the entire transcript.** `_add` does `getattr(event, "emission_sequence", None)` and returns early on `None`, which cannot distinguish "this event has no sequence" from "crewai renamed the attribute". After such an upgrade every entry is dropped, and the CLI reassuringly prints "No transcript was captured for this run." The conformance test would catch it, but only where crewai is installed (see the `importorskip` hole above).
- **`_format_transcript`'s line format is ambiguous and unbounded.** A content line reading `    [7] design / architect (agent_message)` — trivially produced by an agent quoting a prior transcript, which is common in multi-agent runs — is indistinguishable from a real header to any grep or parser, and there is no length cap on a transcript that captures every turn. If the transcript ever needs to be machine-read (Story 4.2), it wants a structured serialization rather than this human format.
- **`TranscriptEntry` carries no run identity.** A streaming or HTTP consumer serving concurrent runs needs to know which run an entry belongs to. Adding a field later is, by AD-13/AC-7's own wording, "a change to the entry type" — the thing the seam was designed to avoid. Worth settling before Story 4.2 builds on the current shape rather than after.
- **Widening `RunResult` changed its generated `__eq__`, `__repr__` and `asdict` output.** Two results that compared equal before (same final output, same per-task results) now differ if their transcripts differ, and `repr(result)` — in a log line or a pytest assertion message — now dumps the entire agent conversation. No existing consumer depends on either today; noted so the next one is not surprised.

## Deferred from: story-2.0 implementation (2026-08-03)

- **Compose sessions do not survive anything.** The registry is a plain in-process `dict` (`api/sessions.py`), so a conversation is lost on every process restart — including each `--reload` restart during development, which happens on every file save. It is also why the API is **single-worker**: a second uvicorn worker gets its own empty registry and roughly half of all requests answer `session_not_found` for a session that is very much alive in the other process. `make api-serve` pins `--workers 1` and the app logs a startup warning if `WEB_CONCURRENCY` disagrees, but nothing *enforces* it. AD-11 defers persistence deliberately, and AD-3 says "one deployable process by default", so this is a known v1 boundary rather than a bug — but the moment anything wants two workers, a shared session store has to land first. PRD Open Question 3 (a stable Team reference) is the natural place to settle what, if anything, outlives a process.
- **`model_substitutions` is derived by re-deriving, not by observing.** `normalize_team_routings` mutates the team in place and reports substitutions only to **stderr** (`model_resolver.py:156-185`), so `api/build.py` reconstructs the *requested* routing by running the same public template the pipeline runs (a pure in-memory transform) and diffing it against the built team. That is accurate for the template path and touches nothing under `team_maker/`, but it has two gaps: it reports `[]` for the **planner path** (empty `desired_roles`, where the team is invented by an LLM and there is no client-requested model to compare against), and it silently degrades to `[]` if the pre-resolution ever raises. The clean fix is for `normalize_team_routings` to *return* its substitution list instead of printing it — a small, obviously-correct change to `team_maker/`, deliberately not made here because AC 12 froze every existing module under `team_maker/`. Whoever unfreezes it should also make the API stop re-deriving.
- **The build path can still trigger a silent second LLM call.** An empty `desired_roles` flips `PipelineRunner` into the planner strategy, which calls a *different* provider config (`planning_llm`) and costs money with no signal (`runner.py:66-69`, `llm/planner.py:24-46`). `PUT /api/compose/sessions/{id}/spec` rejects an empty roles list, and the Composer's system prompt requires at least one role, so the reachable paths are covered — but `POST .../build` itself does not guard, because Story 2.0's Task 3 scoped the guard to the edit route only. A spec that reaches the session with no roles by some future path would build at planner cost, silently.
- **`normalize_team_routings` ignores an explicit key file.** It is called with no config (`runner.py:144-145`) so it re-reads the *default* Key Config path. Harmless today because the API resolves one Key Config at startup from the same default path, but it becomes wrong the moment a request can name a key file.
- **A keyless provider's failures are all classified as unreachability.** `api/routers/compose.py` maps any non-`ComposerError` exception from a `keyless_local` provider (today only `ollama`) to `authoring_unavailable`, on the reasoning that a local, credential-free provider essentially only fails because nothing is listening. It is a data-driven branch on the catalog row rather than on provider name, and it is what AC 10's "a keyless provider can only produce this error for a connection failure" asks for — but it does mean a genuine bug inside a keyless adapter would be reported to the user as "start your local provider". Distinguishing them properly means recognising SDK-specific connection-error types in `api/`, which would put provider knowledge back into the layer AD-8 exists to keep it out of.
- **No CI lane runs `pytest` or `npm test`.** Inherited, not new — Epic 1 logged the Python side and Story 2.1 logged the frontend side. Story 2.0 adds a third suite (`tests/api/`, 89 tests) with nothing automated watching it, and two of its guards (the AC 3 concurrency proof and the AC 4 credential sweep) are exactly the kind that rot silently when only run by hand.
- **The CLI is still Anthropic-only.** `api/` now selects its authoring provider parametrically (AC 10), but `team_maker/cli.py:37-38` remains hardcoded to `anthropic`, and `compose --provider` does not exist. The asymmetry is deliberate — `cli.py` was outside Story 2.0's scope — but it means the same user gets a working Composer in the browser and a dead one in the terminal. The port already exists; this is roughly a `--provider` option plus reusing the same catalog-row lookup `api/deps.py` now does.
- **`api/deps.py` duplicates ~10 lines of `cli.py`'s credential logic on purpose.** `_resolve_authoring_provider` and `_bridged_credential` are private members of the CLI layer; importing them from `api/` would invert AD-4 and drag `click`, `rich` and `PipelineRunner`'s import chain into the API process. The duplication is small and the two are diverging anyway (the API's is parametric and bridges once at startup rather than per call). Promoting a shared credential module under `team_maker/` is the eventual fix and would let the CLI's `--provider` land at the same time.

## Deferred from: code review of story-2.0 (2026-08-03)

- **`fields[].message` carries pydantic-derived text.** `api/errors.py`'s module docstring states as an absolute that *"`message` is authored copy, never `str(exc)`"*. That holds for `error.message` at every raise site, but `error.fields[].message` is the `msg` half of a pydantic or `ComposerError` string forwarded verbatim (`fields_from_composer_errors:116-137`, `fields_from_error_list:140-160`). Pydantic's custom-validator messages routinely interpolate the offending input, and here that input is LLM output derived from the user's intent. AC 8's literal requirement — no traceback, no exception class name — is met, and `assert_no_exception_leak` enforces exactly that, so nothing leaks today. But the guard has no notion of "was this text authored", and the prose above it claims a property one of its two fields does not have.
- **`context_dir` breaks the spec round-trip if the directory disappears.** `PUT .../spec` reconstructs the spec with `TeamCreationRequest(**current.model_dump())`, and `validate_context_dir` (`request.py:374-382`) requires an *existing* directory. If the composer set `context_dir` and it is later removed or unmounted, an unrelated edit such as `{"team_name": "X"}` fails 422 blaming a field the client never sent. Verified. Every other field round-trips cleanly, so this is the single asymmetry — it exists because one validator consults the filesystem.
- **The OpenRouter adapter inherits three robustness holes from its template.** `response.choices[0]` is unguarded (`:83`), and OpenRouter specifically returns an `error` member with an empty `choices` list for upstream model errors, no-credit accounts and moderation blocks — an `IndexError` rather than a diagnosable message. The fallback `json.loads(match.group())` (`:96`) re-raises a bare `JSONDecodeError` instead of the authored `ValueError` the sibling branch produces. And the `OpenAI` client (with its connection pool) is constructed per call and never closed — invisible in a CLI, accumulating in a long-lived uvicorn process. All three are character-identical to `xai_provider.py`, which is what AC 11 required; fixing one adapter and not the other reintroduces the two-patterns problem that AC explicitly guards against. The honest fix is to fix both, which touches an existing module under `team_maker/`.
- **`_guarded` still cannot tell our bugs from the provider's — but it no longer claims to.** The bare `except Exception` in `api/routers/compose.py` maps everything that is not a `ComposerError` to `compose_failed` (502), so a `TypeError`, `AttributeError` or `KeyError` from a genuine defect in `team_maker/` or in the mapping layer lands in the same branch as a network fault. **Partly resolved at review:** the copy was causally neutral-ised — it used to read *"The authoring provider could not be reached. Please try again."*, which blamed the upstream for our own defects and invited a retry loop that spends money and can never succeed, and now reads *"The team specification could not be created. Retry once; if the problem repeats, stop and report it."* Containment was always correct and is regression-tested end to end (`test_an_internal_typeerror_during_refinement_is_contained_and_neutral`). **What remains deferred is the classification itself**: distinguishing a connection failure from an internal defect means recognising SDK-specific exception types (`APIConnectionError`, `APITimeoutError`, and their vendor equivalents) inside `api/`, which puts provider knowledge back into the layer AD-8 exists to keep it out of. Deliberately not attempted in Story 2.0. The clean shape is probably a small classification helper in the adapter layer — where provider knowledge already lives — that maps an SDK exception onto a port-level category the API can branch on as data. That would also let the keyless-`ollama` trade-off logged above be retired at the same time, since both are the same missing abstraction.
- **`include = ["api*"]` claims a generic top-level package name.** The edit is required by AC 5 and is correct for the editable install, but it also ships a top-level `api` package into site-packages in any wheel. That is an unusually generic name to claim and will collide with any other distribution doing the same. Nothing breaks today because the project is only ever installed editable, but a future `pip install team_maker` alongside another package exporting `api` is a real conflict. Worth settling alongside the packaging question in the story's Open Question 5.
- **`fields_from_composer_errors` assumes a `loc` never contains a colon.** It splits on the first `": "` (`api/errors.py:130`) and the inline comment asserts the loc segment is only joined role names and list indices. `sandbox.extra_env` is a `Dict[str, str]` (`request.py:127`) whose keys are arbitrary strings, so a validation failure under a key containing `": "` yields a wrong, unaddressable field path. Low reachability — it needs the authoring LLM to emit a colon-bearing dict key that also fails validation — but the stated invariant is not true, and Story 2.2's inline validation reasons depend on these paths.
- **Reading a spec mutates it.** AC 2 authorises no `GET` session route, so the only way to read the stored spec back is `PUT .../spec {}`, which runs the full merge-and-reconstruct path and replaces `session.current` with a re-validated object. Verified idempotent for every payload the suite exercises, and the story's own tests use it this way — but it is a write pretending to be a read, and Story 2.2's review mode should not lean on it without either a real read route (an AC 2 contract change) or an explicit note that the round-trip is load-bearing.
- **The build path still does not guard empty `desired_roles`.** Already logged above under the story-2.0 implementation entry; the code review confirmed it independently and adds that `PUT .../spec` conversely *rejects* an untouched planner-path spec with a 422 blaming `desired_roles` — a field the client never sent. The two guards are inconsistent with each other: the edit route treats an empty roles list as invalid, while the build route treats it as a supported planner path.

## Deferred from: story-2.2 implementation (2026-08-03)

### Contract friction found against Story 2.0's endpoints

- **`output_exists` tells the user to do the one thing the UI is forbidden to offer.** The 409 copy reads *"Choose a different output path, or remove the existing directory."* (`api/build.py:31-34`), but `output_path` is server-owned and read-only to the browser (2.0 AC 13), so the Composer has no "choose a different path" affordance and is explicitly barred from adding one. The remaining advice — remove the directory — is an instruction to go and use a file manager on the server's filesystem. The message is rendered verbatim because it is authored server copy and Story 2.3 owns error-copy refinement, but it currently asks for an action the surface cannot support. Captured live: `web/tests/composer/fixtures/error-output-exists.json`. The natural fixes are either a server-side de-duplicating path (e.g. `article_team-2`), or an explicit overwrite affordance, neither of which this story may add.
- **A second build in the same session can only ever fail.** `output_path` is derived once from the first spec and pinned for the session's life, so once a build succeeds, every subsequent build of that conversation returns `output_exists` — including after a refinement that legitimately changed the team. The user's only route to a second package is to start a new conversation, which also throws away the transcript. Reachable in one click and confirmed live (two `POST .../build` calls, 200 then 409).
- **There is still no read route for the spec.** Already logged under the 2.0 review as "reading a spec mutates it". Story 2.2 does **not** lean on `PUT .../spec {}` as a read — the editor seeds from the spec already returned by the last create/message/save — so the load-bearing round-trip that entry warned about was avoided. Recorded here only to confirm the warning was heeded.
- **`compose_failed` could not be provoked at all.** A deliberately bogus authoring model (`{"provider":"anthropic","model":"claude-not-a-real-model"}`) returned **201** with a perfectly good spec rather than faulting, so the adapter evidently does not validate or reject the model id it is handed. That means an authoring model typo is silently ignored and the request is served by some other model, with nothing reported to the user. Worth a look on the adapter side; it also left `compose_failed` as one of four codes with no captured fixture.

### Left open by this story

- **`turn_cap_reached`, `compose_failed`, `build_failed` and `session_busy` have no captured fixture.** They need 20 real LLM turns, an unprovokable fault, an induced internal error and a race respectively. Their tests synthesise the envelope from the server's own copy strings and say so out loud (`web/tests/composer/fixtures/index.ts`, `error-paths.test.tsx`). If any of those four messages is reworded server-side, the frontend tests will keep passing against stale copy — a real, declared gap that a shared contract fixture (or a server-generated error catalogue) would close.
- **The transcript does not survive a reload, by design and without any warning to the user.** The API keeps no chat history, so the conversation exists only in React state. A refresh loses it silently. `sessionStorage` would fix the common case, was not specified anywhere, and is deliberately not invented here.
- **Task dependencies are displayed but not editable.** The editor shows "Runs after X" and sends the list back unchanged. A client-side check rejects a dependency naming no task (which the server does *not* check — the template prunes dangling dependencies in silence), but re-ordering the DAG is not possible from the UI.
- **No provider/model picker for the authoring turn.** `authoring` is omitted on every request, so the server default is always used. The story explicitly does not require the picker, and `authoring_unavailable` already names the provider and Key Config entry when the default is unusable.
- **No browser test lane.** `web/tests/composer/e2e-live-check.mjs` is a manual harness — real Chromium against real servers, run by hand, not collected by vitest and depending on a `playwright` install that is deliberately not a project dependency. It passed at implementation time (see the story's Completion Notes) but nothing runs it automatically, so it will rot exactly like the guards the 2.0 review flagged. Wiring a real E2E lane is a Test Architect task (`bmad-testarch-framework`), not a Composer one.
- **`components/ui/popover.tsx` is installed and unused.** Task 1 required installing it; the editor needs no second layer because the provider control is a native `<select>`, which caps modal depth at one more simply than a correctly-nested Popover would. Left in place rather than deleted, since it is vendored, regenerable output and Story 2.4's badge picker is its likely first consumer.
- **Autoscroll is unconditional.** The transcript scrolls to the end on every append, with no scroll-anchoring and no "you have scrolled up" suppression, so a user reading back up is yanked to the bottom when a turn lands. Specified nowhere; the simple behaviour was chosen deliberately and Story 2.4 inherits it.
- **Story 2.1's light-mode primary contrast (4.12:1) is now user-visible.** It is on the `Run it now` and `Build team` labels, which are normal-size text below AA's 4.5:1. Not changed unilaterally — see Open Question 1 in the story file, still unresolved and now shipping on a real surface rather than a placeholder.
