## P2-F1 — "My Teams" has no working save path in this build; it is permanently empty no matter how many teams you build and run

- Persona: 2 (normal knowledge worker). Journey stage: Build → "save for later" / My Teams.
- Steps:
  1. Built and ran 3 different teams in this session (`tagline_forge`, `competitor_pricing_researcher`) plus a pre-existing one from an earlier persona's session (`weekly_planner`) — all present on disk under `generated_teams/`, all built successfully, one run to full completion.
  2. Navigated to "My Teams" (`http://localhost:3000/my-teams`) at multiple points, including after the full run completed. It always shows "No teams yet. Describe one, or start from a template."
  3. Confirmed this isn't a browser-tab/session artifact by calling the underlying API directly: `fetch('/api/teams')` → `{"teams":[]}`, every time, regardless of how many teams had just been built/run.
  4. Read the backend source (`api/routers/teams.py`): "My Teams" / `GET /api/teams` lists rows from a SQLite table (`data/teams.db`) that is populated *only* by `POST /api/teams/save` — a distinct, explicit save action, separate from Build. Build alone never inserts a row.
  5. Searched the entire Next.js frontend (`web/app`, `web/components`) for any reference to that save endpoint or to a "Save" UI action: **zero matches**. The only "save" references in the frontend are (a) `composer-surface.tsx`'s `saveSpec`, which is an unrelated feature — saving a manual JSON edit of the in-progress spec, not saving-to-My-Teams — and (b) `workspace-surface.tsx`'s call to `record-run`, which only updates stats for a team that *is already* in My Teams and explicitly comments that a freshly-built, never-saved team 404s "harmlessly" on that call.
  6. There is no dialog, modal, or button anywhere in the built/run UI that surfaces a save prompt — checked via DOM query for `[role=dialog]` and any element containing "save" (case-insensitive) after the run completed. Confirmed empty.
- Expected: Either Build auto-saves the team into My Teams (so it can be found again later, per the audit's stated success criterion), or there is a discoverable, explicit "Save" action somewhere in the compose/build/run flow that does.
- Actual: The backend fully implements named-team persistence (save/rename/delete/browse, referenced in code comments as already-shipped "Story 2-5" and "Story 2.8" features) — but the frontend never calls it. "My Teams" is a dead-end nav item: it exists, it looks functional (proper empty state, not an error), but no path in the current UI can ever populate it. A user who builds and runs a team, closes the tab, and comes back later expecting to find their work in "My Teams" will find nothing, with no error or explanation — the team simply isn't there, and there was never a moment where the product told them it wouldn't be.
- Severity: **P1** (arguably borderline P0 under "capability silently disappears" — a named, prominently-placed nav item ("My Teams") that promises persistence delivers none, with no in-product signal that anything is missing).
- Evidence: `fetch('/api/teams')` → `{"teams":[]}` (captured live, this session); `C:\Projects\CoinPela\Projects\team_maker\api\routers\teams.py` (backend, confirms save is a distinct explicit action backed by SQLite); grep of `C:\Projects\CoinPela\Projects\team_maker\web` for `save`/`Save`/`/teams/save` returns matches only in test files (`web/tests/composer/route.test.tsx`, `web/tests/my-teams/my-teams-surface.test.tsx`) and the two unrelated frontend features named above — no production call site to `POST /api/teams/save` exists.

## P2-F2 — Navigating away or reloading during (or right after) a run wipes all visible trace of it; the server keeps running but the UI has no way to reattach

- Persona: 2. Journey stage: Run / Workspace.
- Steps (reproduced twice, both on `tagline_forge`):
  1. Started a run (goal: a short "Sunrise Loaf" bakery tagline test) from the workspace. Confirmed via `document.body.innerText` it showed "Running" / "3 tasks" / "Run started."
  2. Reloaded the same URL (`http://localhost:3000/teams/tagline_forge`) ~5 seconds later. The page reset to a pristine "Give this team a goal" empty state, all 3 tasks showing "Queued" — as if no run had ever been started. The prior chat message (the goal text just sent) was also gone from the visible history.
  3. Typed a new goal and clicked Run. Got a hard rejection: **"Another run is already in progress. Wait for it to finish before starting another — this server runs one at a time."** — proving the original run was, in fact, still executing server-side the entire time; the UI reload had simply lost all knowledge of it, with no warning, spinner, or banner suggesting a run might still be active.
  4. Waited (~4 minutes of retrying) for that orphaned run to finish; only then could the real goal (Northbound Coffee) be submitted and run to completion.
- Root cause (confirmed via source, `api/routers/run.py`): `POST /api/runs` returns a `run_id` and the run continues on a server-side thread (`state.run_registry`), polled by the client via `GET /api/runs/{run_id}`. Nothing persists that `run_id` to the URL, localStorage, or any per-team "current/last run" lookup — a full reload has no way to rediscover it. There is also no "list runs for this team" endpoint, so even a determined user has no in-product way to recover a run they lost track of.
- Also revealed in the process: the run-in-progress lock is **global across the whole server, not per-team** ("this server runs one at a time") — if any team's run is active, every other team's Run button will be rejected with the same message, with no queue position or ETA shown.
- Why this matters: a normal knowledge worker will routinely trigger this by accident — clicking a sidebar link, hitting refresh out of habit, or their laptop sleeping and the tab reloading. After that, the product gives zero indication that (a) their run might still be going, or (b) it already finished with a result waiting. The only way they'd discover the truth is by trying to start a *new* run and getting a rejection that mentions an "already in progress" run they have no way to see, inspect, or wait on with feedback.
- Severity: **P1** (core journey state is silently lost with no reasonable recovery path; the failure mode is confusing rather than catastrophic, since the underlying run is not actually lost server-side, but the user has no way to know that).
- Evidence: `document.body.innerText` dumps captured before and after the reload (before: "Running / 3 tasks / Run started."; after: "Give this team a goal" + all tasks "Queued"); the literal rejection string is quoted above, captured live; source: `C:\Projects\CoinPela\Projects\team_maker\api\routers\run.py` (`create_run`, `get_run` — no run-id persistence or run-listing endpoint exists).
