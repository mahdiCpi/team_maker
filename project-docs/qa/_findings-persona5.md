**Usability / trust observations:**
- A founder persona iterating quickly through multiple unrelated team ideas in one sitting (very plausible behavior — "let me also try...") is specifically exposed to the session-bleed defect (P5-F1), because the natural instinct after seeing a proposal you don't like is to click the prominent "New Team" sidebar item rather than remembering that only a hard reload actually clears state.
- The E2E pitch-review scenario (P5-F4) is a worst-case demonstration of "does what's said match what's built, match what actually runs": a founder asked specifically for a brutal, complete pressure-test before a real pitch, got a confident "Objection-Proofed. Nothing in the UI would tip off a founder who didn't read the entire transcript character-by-character.

## P5-F1 — "New Team" nav link is a no-op once already on the compose route; an unrelated follow-up message can silently graft onto a stale, unrelated conversation's role chain instead of starting fresh

- Persona: 5 (startup founder). Journey stage: Compose (session/navigation boundary).
- **Root cause, source-confirmed**: `web/lib/nav-items.ts` defines `{ title: "New Team", href: "/", ... }` — a plain link to `/`. `web/components/app-sidebar.tsx`'s `NavItem` renders it as `<Link href={item.href} />` with no `onClick` handler. `web/components/composer/composer-surface.tsx` holds all conversation state in a `React.useReducer` local to the mounted component (comment in the file: "a reload genuinely loses the conversation... a property of Story 2.0's design"). Because Next.js does not remount a client component when a `<Link>` targets the *current* route, clicking "New Team" while already on `/` triggers no navigation and therefore no state reset — the composer keeps whatever conversation was already open, whether that's a stale, hours-old, unrelated team, or one already built.
- **Reproduction 1 (initial discovery, unplanned)**: browser tab was left mid-conversation from a prior persona's session (`twitter_scraper → data_analyst → summary_writer`, model-preference question pending). Without navigating away first, sent a completely unrelated first message for this persona's scenario 1: "I need a team to help me think through product strategy for a new feature -- market fit, prioritization, and a skeptical gut-check before I commit engineering time." Expected: a fresh team proposal for the new domain. Actual: `team_maker`'s reply was "Updated: twitter_scraper → data_analyst → summary_writer → market_fit_analyst → prioritization_strategist → devils_advocate..." — it kept all 3 of the old, unrelated Twitter-trend roles and simply appended 3 new product-strategy roles onto the same role chain, treating the entirely new domain as a continuation of the old one. Evidence: `project-docs/qa/evidence/p5_s1_session_bleed.png`.
- **Reproduction 2 (controlled)**: hard-reloaded to a genuinely clean session, composed team A ("a birthday party planning checklist for a 10 year old's party" → `theme_and_decor_specialist → food_and_cake_planner → activities_and_entertainment_coordinator → guest_and_invitation_manager → logistics_and_budget_coordinator`, proposal only, not built). Clicked the sidebar "New Team" link (confirmed via DOM query it is an `<a>` and the click handler fired). The page did not change: `document.body.innerText` immediately after the click still showed the full birthday-party conversation and role list. Then typed a plain, unrelated follow-up with no explicit "start over" framing: "Forget that. I need a completely different team: help me draft investor pitch talking points, and have a brutally skeptical VC poke holes in them." — in this case, because the message *itself* explicitly said "forget that... completely different team," the compose backend correctly discarded the birthday-party roles and proposed a clean `pitch_drafter → skeptical_vc` team. This shows the *only* thing that reliably resets a stale conversation short of a hard reload is the user explicitly saying so in natural language inside the same stale session — the "New Team" button itself never does it.
- Why this matters: a founder persona realistically clicks "New Team" — a prominently placed, clearly-labeled sidebar item with its own keyboard shortcut (`g n`) — expecting exactly what its name says. Instead, depending on how the next message is phrased, they either (a) get lucky and the LLM infers a topic change from wording alone (repro 2, explicit "forget that"), or (b) get an unrelated team silently spliced onto whatever was already open (repro 1, no explicit signal) — with no error, no warning, and no way to tell from the UI that "New Team" did nothing. A user who doesn't scroll up to check the full chat history could build and ship a team that's actually a hybrid of two unrelated requests without ever realizing it.
- Severity: **P1** — core "start a new team" journey silently fails under a common, foreseeable usage pattern (composing consecutively without a page reload), with no error and inconsistent, message-wording-dependent recovery. This is a variant of the audit's "capability silently disappears" class: the *button* labeled "New Team" does not actually deliver a new team unless the user also says so in words.
- Evidence: `web/lib/nav-items.ts` (lines 12-16), `web/components/app-sidebar.tsx` (`NavItem`, lines 22-55, plain `<Link>`, no reset handler), `web/components/composer/composer-surface.tsx` (lines 44-49, doc comment confirming state lives only in mounted component state); `project-docs/qa/evidence/p5_s1_session_bleed.png`; live `document.body.innerText` captures for both reproductions (quoted above).

## P5-F2 — "Swap out the most expensive agent" is a no-op disguised as an action once every role is already on the cheapest model; the two earlier cost/merge requests, by contrast, were genuinely real

- Persona: 5 (startup founder, non-technical phrasing throughout). Journey stage: Compose/refine. Team: `weekly_newsletter_team` (newsletter_drafter → fact_and_tone_checker → copy_editor, all `anthropic` by default).
- **Step 1 — "Can you make this cheaper to run?"** Raw response body (`Network.getResponseBody` on `/api/compose/sessions/{id}/messages`) shows a new top-level `"default_llm":{"provider":"anthropic","model":"claude-haiku-3-5"}` field appeared — a genuinely cheaper model tier than the prior `claude-sonnet-4-6`, not a relabeled duplicate. Chat text: "Updated: newsletter_drafter → fact_and_tone_checker → copy_editor. Anything you would change about copy_editor, or is this ready to build?" — no mention of cost/model at all (confirms the already-logged generic-acknowledgment pattern; not counted as new).
- **Step 2 — "I don't need three specialists, merge two of them."** Correctly collapsed `fact_and_tone_checker` + `copy_editor` into a single `reviewer_and_copy_editor` role (verified in the raw spec: 3 roles/3 tasks → 2 roles/2 tasks, with `review_and_copy_edit`'s description literally the concatenation of the two original tasks' descriptions). A real, correct structural edit.
- **Step 3 — "Swap out whichever agent is the most expensive for something more budget-friendly."** Raw response body shows: `newsletter_drafter` gained an explicit `"llm":{"provider":"anthropic","model":"claude-haiku-3-5"}` override; `reviewer_and_copy_editor` got no `llm` field at all (i.e., it stays on `default_llm`, which is *also* `claude-haiku-3-5`). **Both roles end up on the exact same model as before this message was sent** — the "expensive" role that got "swapped" was already on the cheapest tier via `default_llm`; the visible change is only a redundant explicit tag naming the identical model. There was no agent left in this team that was actually more expensive than any other to swap.
- Confirmed at the build/ground-truth level: `generated_teams/weekly_newsletter_team/routing_config.yaml` shows both `newsletter_drafter` and `reviewer_and_copy_editor` routed to the identical `anthropic / claude-haiku-4-5-20251001` (a valid model id the resolver silently substituted for the spec's non-existent `"claude-haiku-3-5"` — this substitution was not disclosed anywhere in the chat, unlike Persona 3's model-substitution case which *was* explicitly disclosed as "one model was not available and a near match was used instead"; disclosure of this auto-substitution is therefore inconsistent, not absent-by-design).
- Chat text for step 3: "Updated: newsletter_drafter → reviewer_and_copy_editor. Anything you would change about reviewer_and_copy_editor, or is this ready to build?" — identical boilerplate to every other turn. A user reading only the chat has zero way to know that: (a) nothing about cost actually changed this turn, (b) there wasn't actually a "most expensive" agent to swap in the first place, or (c) the model name in the spec doesn't match a real Anthropic model id and was silently corrected.
- Why this matters: this is precisely the audit brief's named risk for this scenario — "did 'cheaper' result in an actually cheaper model, or just re-use the same model with new words around it?" The answer here is split: the *first* cost request (step 1) was genuinely honored; the *third* request (step 3), on a team that was already fully cost-optimized, produced the appearance of action (a new field in the spec, an "Updated: ..." message) with zero actual effect, and no disclosure that the request had, in effect, nothing left to do.
- Severity: **P2** — not a functional break (the team still builds and runs fine, and is genuinely cheap), but a real "did the product actually do what I asked, or just perform having done it" mismatch, which is the audit's central concern applied to cost/model management specifically.
- Evidence: raw response bodies for all 3 turns (`Network.getResponseBody`, quoted above), `generated_teams/weekly_newsletter_team/routing_config.yaml`.

## P5-F3 — "Make the skeptic even harsher" tone escalation is a real, substantial spec change, not just a chat acknowledgment — confirms the positive pattern from Personas 2/3, chat text itself remains uninformative

- Persona: 5. Journey stage: Compose/refine. Team: `pitch_and_critique` (pitch_drafter → skeptical_vc).
- Initial build from "I want a team where one agent drafts investor pitch talking points and another agent is a brutally skeptical VC who pokes holes in it" proposed `pitch_drafter → skeptical_vc` with a reasonably harsh `skeptical_vc` already ("ferociously critical, zero-tolerance venture capitalist").
- Sent: "Make the skeptic even harsher, I want to be truly pressure-tested before I pitch for real."
- Chat's reply: "Updated: pitch_drafter → skeptical_vc. Anything you would change about skeptical_vc, or is this ready to build?" — the same generic role-chain template already logged repeatedly by Personas 1-4 (not re-logged as a new finding here).
- **Verified via raw `Network.getResponseBody` on the `/api/compose/sessions/{id}/messages` POST** that the underlying spec changed substantially and specifically toward harsher: `skeptical_vc.goal` became *"Destroy every weak argument, unsupported claim, and overlooked existential risk in the pitch. Leave no stone unturned. The goal is to make the pitch fail NOW so it doesn't fail in front of real money. If a claim cannot survive this room, it cannot survive a term sheet."* and `backstory` became *"A legendary, feared VC partner with 25+ years of experience who has killed more deals than most partners have seen... reputation for making founders cry in pitch meetings, not out of cruelty, but because delusion is expensive... treats every pitch as guilty until proven innocent and demands receipts for every single claim."* A third task, `revise_pitch` (pitch_drafter revises based on the critique), was also added at this turn.
- Confirmed the harsher text persisted into the actually-built package: `generated_teams/pitch_and_critique/agents/skeptical_vc.yaml`'s `goal:` field contains the exact "Destroy every weak argument... cannot survive a term sheet" text verbatim.
- Severity: **N/A (positive finding)**, included for balance and because the audit brief specifically asked to verify this rather than assume it. The only defect here is the already-logged generic-chat-acknowledgment pattern (not re-counted).
- Evidence: raw response body for the "make the skeptic even harsher" turn (quoted above, captured via `cdp("Network.getResponseBody", ...)`), `generated_teams/pitch_and_critique/agents/skeptical_vc.yaml`.

## P5-F4 — CONFIRMED, full E2E run: a compounding pair of silent mid-generation truncations plus an unrequested scope violation leave the final "battle-hardened, investor-ready" deliverable missing exactly the sections (Team, funding Ask) a real investor pitch needs, with the run banner showing "Complete" throughout and zero disclosure anywhere

- Persona: 5 (startup founder). Journey stage: full lifecycle, Build → Workspace → Run → Transcript. Team: `pitch_and_critique` (pitch_drafter → skeptical_vc, tasks `draft_pitch` → `critique_pitch` → `revise_pitch`).
- Goal given: "Draft investor pitch talking points for a startup called RouteWise: an AI-powered logistics routing SaaS for mid-size trucking fleets that claims to cut fuel costs 12% and reduce late deliveries 30%. We're raising a $3M seed round. Then have the skeptical VC tear it apart, then produce a revised pitch."
- All 3 tasks reported **"Done"**; the run banner showed **"Complete" / "Run complete."** with no warning icon of any kind. Full transcript captured to `project-docs/qa/evidence/p5_transcript_pitch_and_critique.txt` (116,159 chars) and a screenshot of the completed-but-truncated final panel to `project-docs/qa/evidence/p5_pitch_run_complete_truncated.png`.
- **Defect A — scope violation traced to the same generic `expected_output` placeholder Persona 3 flagged as a plausible contributor (P3-F4), now confirmed as an actual cause.** `tasks/draft_pitch.yaml`'s `expected_output` is the generic `"All deliverables for 'draft_pitch' completed and documented."` The `draft_pitch` task's own agent (`pitch_drafter`) correctly wrote a complete, 7-slide first draft (Problem → Solution → Market → Business Model → Traction → Team → Ask, transcript lines 225-408) — but then, apparently reading "**All** deliverables" literally, continued unprompted into a self-written `## DELIVERABLE 2: SKEPTICAL VC TEARDOWN` section (transcript line 420) — fabricating three "OBJECTION" paragraphs in the voice of the VC role that had not run yet — before this out-of-scope content itself cut off mid-sentence at *"Your competitive moat isn't 'we"* (line 440).
- **Defect B — the real `critique_pitch` task (run by `skeptical_vc`) is independently truncated too.** Its actual critique (transcript lines 680-912, structured differently from the drafter's fabricated preview — "OBJECTION 1: ... / Problem A — Selection Bias / Problem B — Attribution Methodology / Problem C — Duration" — confirming this is genuinely the VC agent's own independent writing, not a copy of the drafter's fabrication) is cut off mid-sentence at *"Your longest customer relationship is presumably under 18 months"* (line 912/1146, identical cutoff point reproduced in both the live "Message" stream and the "Task completed" restatement — the same double-capture confirmation method Persona 3 used to rule out a rendering artifact). The task's own description explicitly required the critique to *"enumerate the top deal-breaker risks explicitly"* and to *"say so plainly"* if the pitch cannot survive — neither ever happens; the critique stops partway through its third objection.
- **Defect C — the final `revise_pitch` deliverable (the one shown in the workspace's primary panel) inherits the truncated critique with zero disclosure, and is itself also truncated before reaching Team/Ask.** Its opening line confidently states: *"This revised pitch directly incorporates the four major objection categories surfaced in VC teardown... Every slide has been restructured to get ahead of these objections... The best defense is a proactive one."* — with no hedge that the "VC teardown" it claims to incorporate was itself incomplete. The revision then reproduces Slides 1-6 (Problem → Solution → "How We Know What We Know" → Market → Moat → Business Model) in more detail than the original draft, but generation stops mid-table at *"...NPS of 72, and two existing customers who have already expanded from pilot to full fleet. These are early but directionally consistent"* (transcript line 1306) — never reaching Slide 7 (Team) or Slide 8 (The Ask), i.e. the funding amount, use of proceeds, and team-credibility sections that were present in the *original, unrevised* draft and are arguably the two most decision-critical slides in any real seed pitch.
- **Positive finding embedded in the same run**: despite the above, the two agents' actual writing is genuinely distinct and sequential where it did complete — `pitch_drafter`'s real draft and `skeptical_vc`'s real critique use different structures, different phrasing, and the critique responds specifically to numbers and claims from the draft (e.g. directly quoting "7 customers and 847 trucks"). This is not one agent's text copy-pasted three times; the underlying multi-agent mechanics are sound. The defect is entirely in generation-length handling and the complete absence of any disclosure or detection layer around it.
- Why this matters: this is the audit's single most important check — "does what's said match the visible spec, match what's built, match what actually runs" — failing at three compounding points in one short (3-task) run, in exactly the scenario this persona was told to prioritize as the E2E test candidate, and with the highest real-world stakes of any scenario tested this session (a founder taking this "Investor-Ready" label at face value would walk into a real fundraising conversation without a rehearsed Ask). It also extends Persona 3's P3-F4 finding from "plausible contributor" to a directly observed root cause: the generic `expected_output: "All deliverables for '<task>' completed and documented."` field is not just unhelpfully vague, it actively invited one agent to draft another agent's not-yet-run output.
- Severity: **P1** (same class as F8 / P3-F2, third confirmed instance of this defect family) — **arguably P0-adjacent** for this specific run given the real-world consequence (missing Ask slide in an "investor-ready" pitch deck) and the fact that two independent truncations plus a scope violation all went completely undetected and undisclosed by every layer of the product (task validation, run status, chat, transcript UI).
- Evidence: `project-docs/qa/evidence/p5_transcript_pitch_and_critique.txt` (116,159 chars; cutoffs at lines 440, 912/1146, 1306), `project-docs/qa/evidence/p5_pitch_run_complete_truncated.png`, `generated_teams/pitch_and_critique/tasks/draft_pitch.yaml` (`expected_output` field).
